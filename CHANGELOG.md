# Changelog

What changed in Banana OS, newest first. New entries go at the top of **Latest builds**.

## Latest builds

- **Four images, Java required, the licences and the source** - each release now has `Banana_OS.iso` (64-bit only), `Banana_OS-32.iso` (the 32-bit kernel only), `Banana_OS-mesa.iso`, and the all-in-one `Banana_OS-full.iso` (Mesa, every Unix port with Neovim and Git installed, and Java - `java.bpk` on the image, `/EXTRAS`, installed from it at the start, and after an installed system updated itself from it); the all-in-one is built in a job of its own that adds it to the release afterwards and never holds the release up, while `java.bpk` is now required for a release. Images are made by `tools/mkiso.sh` (`make ISO_KERNELS=64`, `make Banana_OS-32.iso`, `make FULL=1 ...`). The boot loaders start a kernel that is on the image (and say to use `Banana_OS-32.iso` when a 64-bit image meets a 32-bit processor); `update` refuses an image without the kernel the computer runs. Licences: every image has `/LICENSES` (Banana OS's GPL 3, and the GPL 2, LGPL 2.1 / 3, Apache 2.0, MIT, BSD, MPL 2.0, Vim, curl, zlib, OFL texts) and the system `/usr/share/licenses/banana-os`; each port's package carries its upstream licence files, linked at `/usr/share/licenses/<name>/` (`kernel/pkg.c`); THIRD-PARTY-NOTICES now covers every port (with Neovim's and Git's libraries), Java with the OpenJDK trademark note, and LibJS; `java.bpk` has `/usr/java/LICENSES`. Source: `Banana_OS-sources.tar` in each release - every upstream archive the builds used (`tools/collect_sources.py`, with SHA-256) and the repository at the tag.
- **`update` grows the boot area of older installs** - a disk installed before build 250 keeps a 128 MiB boot area; an image bigger than that was refused ("too big for the installed disk's boot area - reinstall"), as was any image bigger than a 256 / 512 MiB install's area. From the live CD / USB stick `update` now grows it to 1 GiB (as a new install has it; 512 or 256 MiB when the files would not fit after that) and moves the ext4 filesystem's start there, the files kept: data lying in what becomes boot area is copied further in, inside the old filesystem; then a new filesystem is made at the new start around every block the old one uses, and its files get the old files' data where it is - folders, hard and symbolic links, owners, permissions and dates made again (`kernel/ext4move.c`). One sector (the MBR's partition entry) switches the disk over; until then the old filesystem is whole, so a power cut leaves the system as it was. The installed system updating itself says to update once from the live stick. `tools/ext4test/run.sh` moves a filesystem with every kind of file, checks each one and e2fsck on both sides, and cuts the power at 19 points of the move (120 in a longer sweep): the old filesystem stays whole every time. That test also found an older journal bug: after a commit, the superblock's in-place copy cleared the recovery flag before the transaction's other blocks were written - a cut between them left a half-applied transaction that Linux would not replay; the flag now stays until all of it is in place. In QEMU: build 212 installed (BIOS and UEFI), updated from the live CD to an image over 128 MiB (the boot area grew to 1 GiB, 1367 files moved in 0.8 s), restarted with its files, links and old programs intact, `fsck` and Linux's e2fsck clean. See [the boot area](docs/INSTALLER-BOOT-AREA.md#growing-the-boot-area-on-update).
- **`/proc`, the Linux way: Minecraft's F3 screen shows the CPU** - a `/proc` made when it is read, as Linux's (`kernel/procfs.c`; never a file, never on the disk): `cpuinfo` (vendor, name, family / model / stepping, MHz, flags; each processor thread with its core and package, from the kernel's own topology - hybrid P/E cores too), `meminfo`, `stat` (each core's busy and idle time, kept by the scheduler), `uptime`, `loadavg`, `version`, `mounts`, `filesystems`, `cmdline`, `swaps`, `sys/kernel/{hostname,ostype,osrelease}`, and `<pid>/` (`stat`, `status` with the user ids, `cmdline`, `comm`, `statm`, `exe`) with `self`; read-only, `cd /proc` and relative paths work, the built-in shell's `cat` reads it too. `/sys/devices/system/cpu` (`online`, each core's `topology/` and `cpufreq/`) is written at every start, rewritten only when it changes. Java's OSHI library reads them: Minecraft's F3 screen says *CPU: 4x Intel(R) Core(TM) i5 ...* instead of *<unknown>*, from 1.12 (OSHI 1.1) to 1.21 (OSHI 6); neofetch shows the CPU too. OSHI 6 (Minecraft 1.19+) also needs **JNA**: the SDK's `dlopen` now loads a library built on Linux that needs only the C library - JNA's own `libjnidispatch.so`, from its jar, whatever its version - `libc.so.6`, `libdl`, `libm`, `libpthread` being the app's own C library (glibc's `_setjmp`, `__strdup`, `__getdelim`, `mkostemp` added). Java apps get it with the next `java.bpk`. Checked in QEMU with Minecraft's own F3 code on OSHI 6.6.5 / JNA 5.14, OSHI 5.8.5 / JNA 5.10 and OSHI 1.1 / JNA 4.4 (all *4x QEMU TCG CPU*; the old java.bpk: *<unknown>* with OSHI 6), with 4 cores and with 2 cores x 2 threads.
- **Users: Files asks an administrator, older apps, SSH** - Files (create, rename, delete, paste, drag and drop) brings up the administrator prompt when your rights refuse something, then does only the refused items again: a refused copy is undone rather than left half-done, so nothing is copied twice. Apps made before API 35 that write to `/home/banana` are sent to the logged-in user's home (Settings > Users, `homecompat on|off|skip <app>`). The SSH server starts once any user has a password, not only banana. `passwd`, `doas` and other questions asked over SSH, the serial line or bash in a Terminal read that terminal's keys even while a desktop window has the focus (they went to the window in front). The `wallpaper` command's choice is kept again after a restart (since users came, a command run as a user could not write `/etc/wallpaper`); the recent emojis and pinned clipboard entries likewise. `theme install` (into `/usr/share/themes`) asks for an administrator.
- **Users, the Unix way** - more users (Settings > Users, `adduser`), each with a private home; files with owners and Unix's permissions for apps and commands (`/etc/shadow` is root's, the system's folders read-only for users, /tmp sticky); `doas` (with `/etc/doas.conf`, `persist`) and `su`; root locked, banana the first user and an administrator (`wheel`). The system's commands that change the system ask for the password in the terminal; on the desktop a small always-on-top window asks Yes / No (or the password: Settings), remembered for 5 minutes by default (0-60). An administrator with no password is never asked - existing installs and the live CD work as before; `/etc/shadow` moves to the standard format at the first start, the password kept. A login screen user picker and *Switch user*; SSH for every user with a password. API version 35: real user and group ids (`getuid`, `setresuid`, `getgroups`, `getpwnam` reads `/etc/passwd`), `auth` (doas, su). Tests: `tools/test_users.py`.
- **Microphones and webcams** - recording from the computer's own input (HD Audio mic or line-in, AC'97 mic) and from USB microphones (headsets, webcams' mics; any rate, made 48 kHz), and USB webcams (USB Video Class: YUY2 and MJPEG, up to 640x480). New **Camera** app (live picture, photos to `~/Pictures`, voice memos to `~/Recordings`), the `mic`, `webcam` and `lscam` commands, and API version 34 (`mic`, `camera`) for apps.
- **`ksnprintf` precision and sizes** - `%.3s`, `%.*s`, `%-17.17s`, `%lx`, `%zu` work in the kernel's printf (they printed themselves and shifted every later argument: the browser's `Date` strings, Task Manager's compact list); gcc now checks every kernel printf-style call's arguments.
- **The home folder starts clean** - no `readme.txt` in a new home (one already there is left as it is), and the example and test apps moved from `~/Examples` to `/usr/share/extras` (an old `~/Examples` holding only them goes at the next start); the App Store lists them under **Extras**.

- **Games: the CPU no longer spins while waiting for the GPU, and the desktop no longer redraws the whole screen for each frame** - two costs every GPU shared (10-15 fps in Minecraft on any card, the CPU at 100%, `banana-sh` alone ~30%): **(1)** waiting for the Radeon to finish (Mesa does it every frame) went through `task_yield()`, which returns at once when nothing else wants the core - the wait spun at 100% CPU; it now spins at most 0.2 ms, then sleeps 1 ms between looks (as the Intel driver already did). **(2)** `banana-sh` is the kernel's main task, which also runs the desktop: every new frame of a game redrew the wallpaper, the icons, every window and the taskbar, then compared the whole screen with the one before. Now, when only the front window's pixels changed, just its client area goes into the desktop's picture, what is over it is drawn again, and only that rectangle is shown. In QEMU (gears, 800x600): the desktop's share 7.0% -> 4.1% of all the cores, gears 18 -> 24 frames a second; at 1920x1080 the whole-screen work saved is ~4.5 times bigger.

- **The disk's free-space map is checked at every start - why install never broke anything but update and repair did** - `fsck` only compared the groups' free counts with their bitmaps; nothing checked that the blocks each file has are marked used. A block of a file marked free (left by an older bug) is where the next file is written: install formats a fresh filesystem, so it was always fine, while an update or a repair writes many files into the existing one - and went over programs that were fine (bash "not an ELF program", the Terminal). Now **every start of the installed system walks every file's extents before anything is written**: a file's block marked free is marked used again, blocks in two files at once (damaged) are counted and named in `dmesg`, and a desktop notification says when anything was found; `fsck` runs the same check. The built-in apps' boot check then puts back the damaged ones. `tools/ext4test/scrub.c` shows the failure (a program's blocks marked free, then files written: the program overwritten) and the fix (the same with the check first: it stays as written), with e2fsck clean. 6,300 files in 117 ms in QEMU.

- **A broken bash no longer locks you out, and `repair` works without the stick** - when bash could not run (damaged on the disk: "exec format error", "not an ELF program"), every console kept trying to start it every 5 seconds and nothing else was left: no shell to run anything in. Now bash's contents are checked before the consoles start it, and if it is damaged - or cannot start twice, or ends as soon as it starts - the console goes to **the kernel's built-in shell**, which nothing on the disk can break, with what happened and what to do. **`repair` now works on the installed system itself** (from that built-in shell too): every built-in app - bash, Terminal, the App Store... - is installed again at the next restart from the system's own copy and read back from the disk; no USB stick needed. And a damaged built-in app is now always put back at the start, also when a newer version of it came from a repository (it was left broken then). Tested in QEMU on UEFI, an AHCI SATA disk and 12 GB (as on the PC that reported it): install from a USB stick, update, repair, starts without the stick; bash overwritten with garbage while running -> "bash cannot start (not an ELF program) - the built-in shell takes over" -> `repair` -> restart -> bash back byte for byte, files kept, `pkg verify` clean; also with the AHCI controller's 64-bit DMA turned off (the bounce path).

- **Java games: VSync works - no more 100% CPU for frames never shown** - LWJGL's GLFW on Banana OS ignored `glfwSwapInterval`: a game with VSync on (Minecraft's default) then never waited for the screen and drew frames as fast as the processor could make them - loading, in the menus and in game, the CPU stayed at ~97% while the frames beyond the screen's 60 a second were thrown away. `glfwSwapBuffers` now keeps the frame rate the game asks for: with VSync on, after each frame it sleeps until the next 1/60 s (a deadline that advances evenly; a frame that came late starts it again). The time the CPU spent on the extra frames is free for the game's other threads, and the GPU draws the frames that are shown. With VSync off, the game's own frame limit (Minecraft's Max Framerate) applies as before.

- **`prof`: what the processor cores spend their time on - and the installed system never reads programs from the USB stick** - `prof [seconds]` looks at every core once a millisecond (the boot core from its timer, the others through an interrupt sent on the same tick) for 10 s and reports: how busy each core was; the tasks (app code / kernel); the system calls the kernel's time went to (taken at the moment of each look); the hottest functions in apps - by library and **function name**, the internal ones too (libOSMesa's 18,000 functions: read from the library file's own symbol table once), Java's generated code shown as such; and the hottest kernel functions (the kernel now carries its symbol table: a second link pass, `tools/mkksyms.py`, which checks that no code moved). The report is also saved in `/home/banana/prof.txt`. Made for "the game takes 100% CPU even in its menu": start the game, open a terminal (Alt+F2), `prof`. `glinfo -loop N` draws frames for N seconds and prints frames a second - a steady load to measure. Also: **a system started from the disk now never reads programs from a stick or CD** - only the live system does; before, an installed system whose disk could not be read fell back to the boot medium's packages, and pulling the stick out then broke its programs. Tested in QEMU: `prof` against a busy loop (95% on one core, in bash) and against `glinfo -loop` (Mesa's softpipe functions by name, the system calls correct), its own cost about 5% of one core under emulation; the live boot checks and the install / update test.

- **An update can no longer be cut off halfway by the USB stick** - `update` (and Settings > System update) read the stick, CD or ISO file and wrote the disk piece by piece, 1 MB at a time: a stick pulled out (or a loose USB port, or a stick that stops answering) halfway left the disk with part of the old system and part of the new one - in QEMU such a disk was no longer even found as a Banana OS install. Now the whole image (118 MB) is **read into RAM first**, checked there against its checksum list - the very bytes that will be written - and only then written to the disk from RAM, and read back. A stick that stops reading leaves the disk **exactly as it was**: "the USB stick stopped reading before anything was written - the disk is as it was". With less than ~310 MB free it streams from the stick as before (logged). Tested in QEMU: the stick unplugged 6 s into an update (on the old code: a disk that is no longer found; now: nothing written, the same build starts, files kept), a staged update from a stick and a restart into it, the streamed one at 384 MB, and the install / update CI test. A power cut during the few seconds the disk is written can still leave it unbootable - the live stick's `update` / `repair` then fixes it, the files kept.

- **Each CPU core in Task Manager, easy to find** - Performance > CPU has a **Show each core / Show overall** button under the graph: a graph per logical processor, each labelled with its number and its % (the view was there, but only by clicking the graph - in a place that no longer matched it - or right-clicking). `taskmgr cores` opens it directly (`taskmgr cpu`, `taskmgr gpu` the others). Tested in QEMU with 4 cores.

- **GPU usage in Task Manager (Radeon HD 5000-7000)** - Task Manager's GPU tile and page now show how busy the graphics card's 3D engine is, with a graph, and the video memory apps hold (of the card's total), where before it said "Its load is not measured". The Radeon driver samples the 3D engine's busy bit (GRBM_STATUS.GUI_ACTIVE, what Linux's radeontop reads) from the 1 ms timer, only while someone looks (Task Manager open, or `gpu load`, which prints the last second's load and the video memory in use) - a register read a millisecond, nothing when nobody looks. Other GPUs still say "not measured". Tested on the model card (`tools/tests/radeon_gfx.sh`: the bit read as idle and busy) and in QEMU (`gpu load` without a Radeon); on a real HD 7450 the number is still to be seen.

- **Update from the installed system, Settings > System update, and the build number** - the installed system now updates itself: plug in a Banana OS USB stick (or CD), or give it the ISO file - `update` / `update ~/Downloads/Banana_OS.iso` in a terminal, or **Settings > System update**, which finds the stick (or a `Banana_OS.iso` in Downloads), shows its build against this one, has *Choose ISO file...*, *Update now* with a progress bar, and *Restart now*. Only the boot area is written, read back and checked against the image's checksum list as on the live stick (a damaged stick or file is refused before anything is written); the running system stays in RAM and **the new one starts at the next restart**, which updates the built-in apps and reads them back from the disk. The live stick's update stays as it was. The stick the system is installed on is never taken for an update source. An install on the old 32 MB layout is told to update once from the live stick. **`build`** (or `version`) prints the build - the release's `build-N`, from CI's run number - and its commit; the image carries it as `BUILD.TXT`, the kernel shell's `uname -a` shows it. Also: **FAT32 sticks read big files in parts** (an ISO, a video: more than 256 KB) instead of loading the whole file into RAM first - a 118 MB ISO on a FAT stick held the shell for 40 s; small files are read in whole and kept as before. Tested in QEMU: an installed system updated from a USB stick holding another build, from an ISO on a FAT32 stick, and from Settings (*Update now* -> progress -> done), each restarted into the new build with its files kept and `pkg verify` clean; a fragmented 9 MB file and the ISO on FAT read back with the right SHA-256, also from the middle; a file that is not an ISO, and no stick, are refused.
- **Update and repair check themselves, and booting the stick by mistake is said** - on a PC whose boot order starts USB first, leaving the Banana OS stick plugged in after an update starts **the live stick again, not the installed system**: its programs then come from the stick (pull it out and the Terminal says "not a valid ELF program"; a stick of another build gives "exec format error"), and the installed system's files, settings and network are not used - which looked like an update or a repair breaking bash and networking. Now: **(1)** the desktop says so when the live stick was started while Banana OS is installed on a disk, and `update` / `repair` end with "NOW REMOVE THE USB STICK, then restart"; **(2)** the image carries a checksum list (`BANANA.SUM`, `tools/iso_sums.py`) of its kernels - every built-in program is inside them - and its EFI image: `update` and `install` read the stick back whole against it before writing anything, and refuse a damaged one (worn out, written badly) with the file that is wrong; **`checkmedium`** runs the same check by hand; **(3)** after an update or a repair, the installed system's first start unpacks the built-in apps and then reads every program and library back **from the disk itself** (written out, the RAM copies and the disk cache let go) against the packages: a file the disk did not keep is installed again, and if it is still wrong a notification and `dmesg` name it. Tested in QEMU: `checkmedium` reads the CD back as built (in the boot checks, CI); install, repair from the CD and a start from the disk reinstall and read back every app, and bash runs.
- **OpenGL on a GPU, the frame pipeline fixed (Minecraft's GPU stuck at 15 %)** - the previous change read each window's frame back through a pixel buffer, but on r600 Mesa does that `glReadPixels` on the processor: it waits for the GPU to finish the frame, copies it into the buffer, and only then lets go - with the HD 7450 the GPU fell from 30 % to 15 % busy and a core sat at 100 %. Traced on the r600 model (every frame went through Mesa's software `_mesa_readpixels`). Banana's OSMesa now does it itself (`OSMesaBananaSnapshot(2)`): at each flush the GPU blits the frame into one of two staging textures in system memory, and the one before - finished meanwhile - is copied into the app's buffer; the app's swap is a `glFlush` and one copy into its window. No `glReadPixels`, no pixel buffers, nothing of the app's GL state touched (the window's framebuffer is bound for the flush and the app's put back, which also fixes frames not reaching the window from apps swapping with their own framebuffer bound). Checked: on r600 every swap is one GPU blit, never the software path; `tools/tests/gl3_host/run.sh` (softpipe and the r600 model) shows each frame a swap later, right side up; the Mesa ISO passes in QEMU. **Update `java.bpk` too** (its LWJGL and libOSMesa carry this).
- **Radeon HD 6500 / 6600 / 7500 / 7600 (Turks) and HD 6790 / 6850 / 6870 (Barts): 3D and OpenGL too** - the 3D engine and Mesa's r600 now run on the two bigger Northern Islands chips as well as on the HD 6450 / 7450 (Caicos) and HD 5450 (Cedar), with `gpu experimental on`: their prefetch-parser microcode from linux-firmware (`firmware/amd`: their ME and memory-controller microcode are byte for byte Caicos'), Linux's golden registers for each, and the engine set up for their shader engines and render backends (Turks: 6 SIMDs, 2 render backends; Barts: two shader engines, 8 render backends). The engine clock apps are told is the video BIOS's. **Not yet run on those cards:** the model command processor brings both up with their microcode checked word for word (`tools/tests/radeon_gfx.sh turks / barts`), and the Linux build of r600 on HD 6670 and HD 6870 models gets "AMD TURKS" / "AMD BARTS" with OpenGL 4.5 and runs 30 frames, every command stream passing the kernel's checker (`tools/tests/radeon_host/run.sh`, in CI).
- **OpenGL on a GPU: the processor and the GPU now work at the same time (faster Minecraft)** - every frame an app showed in its window (`bgl3_swap`, which LWJGL's `glfwSwapBuffers` and so Minecraft use) ended with `glFinish`, and OSMesa then copied the whole frame back to the app: the processor waited for the GPU to finish the frame, and the GPU sat idle while the processor prepared the next - on a Radeon HD 7450 Minecraft kept it at about 30 %. On a GPU (r600, crocus, iris, VirGL) a window's frame is now read back by the GPU itself into one of two pixel buffers while the app goes on drawing, and the frame before is shown from the other: a frame of latency, no waiting. OSMesa leaves those contexts' frames alone (`OSMesaBananaSnapshot`, Banana's OSMesa); the app's GL state is kept as it was, `bgl3_pixels` still gives the current frame, software rendering is unchanged, and `BGL3_SYNC=1` brings the old way back. Tested: `tools/tests/gl3_host/run.sh` (in CI) runs the SDK's code on the Linux build of libOSMesa - with softpipe each swap shows the frame before, right side up, the app's framebuffer, pixel buffer and pack settings untouched; with r600 on the HD 7450 model every one of its command streams passes the kernel's checker; the Mesa ISO's checks pass in QEMU.
- **Radeon HD 7450: the screen no longer breaks up when a game loads (display watermarks)** - with Minecraft on the Radeon's 3D engine, the picture slid sideways (its left part showing on the right), then turned into horizontal and vertical lines that stayed after the game was closed. The display controller fetches the screen from the same video memory the 3D engine was now hammering, and Banana OS never set how early and how urgently it asks for it: the firmware's watermarks, made for a screen alone. The driver now programs them as Linux does (`evergreen_program_watermarks`, in `third_party/radeon/evergreen_wm.c`): latency watermarks and priority marks from the mode, the memory's and engine's clocks (the video BIOS's), the memory channels and the line buffer, with the display's priority always on (as Linux's `radeon.disp_priority=2`) - when the 3D engine starts and at each mode set; `dmesg` shows the values. Linux's fixed point wraps the priority mark for latencies this card has (17 us at 1080p: a mark five times too small); it is computed in 64 bits here (`tools/tests/radeon_wm.c`, in CI). **`gpu radeon dump`** now also saves the kernel log (`radeon-dmesg.txt`), for when the screen cannot show it.
- **OpenGL on the Radeon HD 7450, part 3 of AMD 3D: Mesa's r600 (for Minecraft)** - with `gpu experimental on`, OpenGL apps - Java and Minecraft included - now draw on a Radeon HD 5450 / 6450 / 7450 / 8450 (TeraScale 2: Cedar, Caicos) through **Mesa's r600 driver** (OpenGL 4.5 core). The kernel gives apps Linux's radeon interface on `/dev/dri/card0` (`kernel/radeon_drm.c`): buffers in video memory or the GTT, mapped into the app, and command submission through **Linux's own command checker** (`third_party/radeon/radeon_cs_check.c`, MIT) - these GPUs have no address space per app, so every stream is checked register by register and every buffer address patched in and bounds-checked before it runs on the 3D ring, which starts at the first app. Mesa gets r600, its radeon winsys and libdrm's surface layout code (`R600=1 ports/mesa/build.sh`; r600's shader compiler is C++ with streams, so libstdc++ is linked in as the LLVM port does); it is tried first and only takes a Radeon, then iris / crocus, VirGL, softpipe. `gpu3d off` sends apps back to the processor, `glinfo` shows the renderer ("AMD CAICOS"). **Written without the card, so experimental:** `tools/tests/radeon_host/run.sh` (in CI) runs the Linux build of r600 on the hosted kernel interface and a model of the HD 7450 - an OpenGL 3.3 program gets its 4.5 context and runs 30 frames, every one of its 66 command streams accepted by the checker and run, with no GPU access outside a buffer (the model does not draw: pixels are not checked); `tools/tests/radeon_gfx.sh drm` checks the interface, refusals included; in QEMU (no Radeon) the Mesa ISO's checks pass with r600 in the library, falling back to softpipe. If an app misbehaves on the card, `gpu3d off` and `dmesg` (the checker logs what it refused).
- **Dragging a window no longer pins a core at 100 % (Intel and Radeon vsync)** - with a graphics driver that waits for the screen's vertical blank (Intel HD / UHD, and Radeon with `gpu experimental on`), every frame shown was preceded by a busy wait on the display's frame counter - up to a whole frame (16.7 ms at 60 Hz) spinning at full speed, so moving a window kept one core busy all the time. The wait now learns the refresh period from the counter and sleeps through most of the frame, spinning only the last ~2.5 ms: on a simulated 60 Hz display (`tools/tests/vblank_wait.c`, in CI) 84 % of the waiting is asleep, and each wait still ends within microseconds of the blank.
- **Installing from a USB stick on UEFI PCs fixed ("no hard disk found")** - booted from a USB stick, the PC's UEFI firmware never starts the SATA disk's port, and Banana OS read the disk's signature before turning on the port's FIS receive - the signature it is latched from - so it read ffffffff and skipped the disk: the installer (command line and desktop) found no hard disk. The port is now set up first, the signature read after, with a COMRESET (as Linux) if the disk still has not said what it is; each port's outcome is in `dmesg`. Also **USB devices after a warm reboot**: a USB 2 port on the xHCI controller is now always reset before its device is addressed (as Linux), even when the firmware or the previous session left it enabled - a mouse there worked only from a cold start. And **`dmesg`**: the kernel log is kept in memory (real PCs have no serial port to read it from). Reproduced in QEMU (UEFI, q35, booted from a USB stick, SATA disk): before, "install: no hard disk found"; now the install completes and the disk boots on its own.
- **The pointer dragged to the bottom-left corner on PCs without a PS/2 port, fixed** - on a PC with no PS/2 controller, the firmware's USB emulation answers at the PS/2 ports during boot, so Banana OS took it for a real one; once the USB controller is taken over the emulation stops and the ports read 0xFF, which the mouse driver read as packets of "left 1, down 1, every button held" - the pointer pulled to the bottom-left whatever USB mouse moved it (a Logitech G502 the same as a cheap one), and the keyboard fed junk bytes until replugged. Every read of the PS/2 status now checks for that: three 0xFF in a row (a status no real controller gives) and the PS/2 side is switched off, USB only from then on. The mouse host test replays it (the 0xFF stream moves nothing; a USB mouse still moves the pointer) and fails on the old code; in QEMU without a PS/2 controller (UEFI) the USB keyboard and mouse work on the desktop.
- **The pointer no longer snaps back to a corner** - a device that keeps reporting the same absolute position (a keyboard's or receiver's spare pointer interface, a monitor's touch hub, a board's virtual USB tablet, a parked pen) pulled the pointer back there on every report, so a USB mouse could move it only for a moment before it jumped back to the bottom-left. Now only a change of an absolute device's position (or its own click) moves the pointer; digitizers that say no pen or finger is in range are ignored. **`lsusb`** now shows each USB input interface's role (keyboard, mouse, absolute pointer, game controller), how many reports it has sent and, for an absolute one, where it last put the pointer - to find such a device. Reproduced in QEMU (UEFI, a USB tablet repeating the corner while a USB mouse moves): before, the pointer stayed in the corner; now it follows the mouse.

- **No more "use install" on a damaged disk:** when a disk holds Banana OS
  but its files cannot be read, `update` used to say "use 'install'" - and
  installing erases everything. It now says the files are unreadable and
  that installing would erase them; `install`, `disks` and the graphical
  installer mark such a disk "Banana OS, but its files could not be read".

- **Repairing a broken install:** built-in programs could go bad on the
  disk with their sizes unchanged ("not an ELF program": Terminal, the App
  Store, finally bash), and the check at every start only compared sizes.
  It now also checks the contents (CRC-32C) of the built-in apps' programs
  and libraries and puts a damaged one back from the kernel's copy - after
  an `update` from the CD, a broken bash is repaired at the next start. New
  on the live CD: **`repair`** writes the system again (also when it is the
  same version) and has every built-in app installed again at the next start
  from the disk; files, settings and the password are kept.

- **Clocks to the nanosecond:** `clock_gettime` and `gettimeofday` counted
  whole milliseconds, so Java's `System.nanoTime()` (Minecraft's frame timing
  and frame limiter) moved in 1 ms steps, and two reads a tick apart looked a
  whole millisecond apart (what hung Vim). Apps now read the system's shared
  hardware counter (HPET or ACPI PM timer, API version 33: `uptime_ns`), on
  any core and without leaving it; the wall clock is still one line that never
  runs backwards. Apps built with an older SDK keep millisecond clocks.

- **More reliable updates:** `update` (and `install`) now read the whole boot
  image back from the disk and compare every 64 KB piece with what was meant
  to be written. A piece the disk did not keep is written again, and if it
  still differs the update fails and says so. Before, a dropped write stayed,
  and the checksum table told the next updates it was fine. Every package now
  records its files' sizes and checksums when it is installed (`/apps/<app>/.files`,
  and the files an `unpack=` package such as Java puts in `/usr`). At every
  start the built-in apps are checked by size and put back from the kernel's
  copy if a file is missing or cut short. Apps installed before there were
  lists are installed once more after the update, which also repairs what an
  earlier update broke. **`pkg verify [app...]`** checks every file's
  checksum, repairs a damaged built-in app, and says how to reinstall the others.
- **Vim no longer hangs on `:wq` / `:qa!`:** a peek for input could turn into
  a wait for ever when a millisecond tick fell between two clock reads
  (the intermittent `shelltest -e` failures in CI). The GUI installer's
  **Restart now** uses the system's restart, which tries the chipset reset
  too; it froze PCs that ignore the keyboard controller's reset line.

  64-bit system is now neofetch 7.1.0 itself (the bash script, `ports/neofetch`)

  so the backend reads the new **`sysinfo`** command, which prints the system's

- **Unix processes: fork, exec, wait - terminal remaster, part 2 (build 238)** - apps are real Unix processes now (64-bit). **`fork`** makes a copy of the calling process: a new address space sharing every page *copy-on-write* (read-only in both until one writes it, then that one gets its own copy - `kernel/uspace.c`, page reference counts in `kernel/upage.c`), the same open files, pipes and sockets (build 237's descriptions), the signal handlers and mask; the child goes on from the same system call with 0. To make that possible a program now lives entirely in its own mmap region: the ELF image (built in kernel memory, relocated for where it runs, copied in), its stacks with guard pages, argv, the environment and the call table. **`execve`** replaces the calling program (descriptors marked close-on-exec closed, caught signals back to their default, the other threads gone); `#!` scripts run their interpreter. **`waitpid` / `wait` / `wait3` / `wait4` / `waitid`** with `WNOHANG`; a process that ends while its parent lives stays a *zombie* until waited for, its parent gets `SIGCHLD`; orphans are nobody's. Process groups and sessions (`setpgid`, `getpgid`, `setsid`, `getsid`), `kill` to another process, a group or everyone, `getppid`. In the SDK: the `exec` family (`execl`, `execlp`, `execle`, `execv`, `execvp`, `execvpe` with `$PATH`), `posix_spawn` / `posix_spawnp` with file actions and attributes, `system` and `popen` (they need a `/bin/sh` - coming with bash), `environ` from the system (`HOME`, `PATH`...). Also: each task has its own current folder (a `cd` in one terminal no longer moves the others), the kernel's own writes obey read-only pages (CR0.WP: a write into a shared page copies it), up to 96 processes at once. API version 26. posixtest's new `proc` part: a child's exit code, copy-on-write of data / stack / heap, 100 KB through a pipe between processes, `execve` with argv and envp and stdout into a pipe, a missing program, `kill` with `SIGTERM`, `ECHILD`, `posix_spawn`, `O_CLOEXEC` across exec, `setpgid`, 20 children at once - 11/11. posixtest 95/0 (64-bit), 73/0 (32-bit: `fork` gives `ENOSYS` there), selftest 292/0 and 274/0, installed from and booted off the disk.
- **Unix file descriptors and kernel pipes - terminal remaster, part 1 (build 237)** - first step of replacing the built-in shell and its terminal with real Unix processes, ttys, GNU bash and zsh (the plan: `docs/TERMINAL-REMASTER.md`). A process's file descriptors now point at *open file descriptions* kept by the kernel (`kernel/kfile.c`), as on Unix: `dup`, `dup2`, `dup3` and `fcntl(F_DUPFD)` make more descriptors for the same file, socket or pipe end, sharing its position and flags; close-on-exec flags (`FD_CLOEXEC`, `O_CLOEXEC`, `pipe2` / `socketpair` / `dup3` with it); `F_GETFL` gives the real access mode. 0, 1 and 2 are now descriptors like the others - the terminal at the start, but they can be closed or replaced (`dup2(pipe, 1)` sends `printf` into a pipe). Pipes and AF_UNIX socket pairs moved from the SDK's C library into the kernel (64 KiB, writes up to 4 KiB never mixed with another's, `SIGPIPE` / `EPIPE` with no reader left, poll wakes when the other end acts), so their ends can later be in different processes - a shell's pipelines. `isatty` and `fstat` tell a terminal from a pipe from a socket. A system call working on a descriptor holds it while it runs, so a `close` or `dup2` from another thread cannot free a socket or pipe under a blocked `recv` / `read`. - **ext4: the installed disk's filesystem (build 187)** - an installed Banana OS now keeps its files in **ext4, in ext4's own on-disk format**: Linux mounts the disk (at 128 MiB into it) and Linux's `e2fsck` checks it clean. Until now the files lived in RAM and a task copied them to the disk 2 seconds after each change - a whole file at a time, the whole list of files every time. Now the disk is the filesystem and RAM is a cache: reading or writing a part of a file reads or writes only those 4 KiB blocks, through a block cache that gives memory back when it runs low; an app writing in the middle of a big file, or appending to a log, no longer loads the file into RAM or writes it again. ext4 as Linux has it (kernel/ext4.c): 4 KiB blocks in groups of 32768 with flex_bg, block and inode bitmaps, 256-byte inodes, files as **extent trees** (in the inode, then leaves and index blocks), directories as entries with their file type, symbolic links up to 59 bytes in the inode itself, uninit_bg (a new disk's inode tables are not written whole), owners, modes and dates in UTC. And **the journal - JBD2, ext4's own** (inode 8, 32 MiB): changes are written within half a second as a transaction in ordered mode - the files' data in place first, then the changed metadata into the journal with a commit block, then in place; a power cut leaves the disk as before the transaction or, once its commit block is on the disk, the next start replays it (and so does Linux, or its e2fsck). The swap area is a `/swapfile` in one run of blocks. **An installed disk is moved over by itself** at the first start of this version (after `update`): its files' data stays where it is - each file's inode points at it - only what lies where ext4 keeps its superblock and group descriptors is moved first; until the new superblock is written the disk is still the old one. `fsck` checks the groups' counts against the bitmaps, `df` says ext4. - **Swap, part 2: a swap area on the disk (build 184)** - an installed system now also swaps to its disk. At boot it takes a **swap area** at the top of the disk's free space - as big as the RAM, 4 GB at most, half the free space at most (`swap` shows it; `df` does not count it as room for files) - and when compressing (build 182) is not enough, or a lot is compressed, the **oldest compressed pages are written there** and their RAM freed, as Linux's zswap does. A page an app touches again is read back from the disk in the page fault: for that the page fault no longer runs on its own emergency stack - it runs on the thread's kernel stack, so it may wait, and moves to the processor core that drives the disks first, as a system call does. A page that is being written while it is touched is taken back from RAM; one unmapped while it is on its way is freed by whoever moves it. System calls that run on the other cores with interrupts off and would read app memory that may be on the disk go to the boot core instead. Nothing of the area is saved: an older Banana OS sees free space there. `swap disk` writes the compressed pages out now; `free` and Task Manager show what is on the disk. Tested in QEMU on an installed disk: `selftest swap` (6 checks - 6144 pages to the disk and back, every byte right, from apps on 4 cores; nothing left once unmapped). With 192 MB of RAM, `systest swap 400` (an app filling 400 MB - zeros, text, noise - then reading it all back): 102400 pages read back, 0 wrong, 88882 pages written to the 169 MB swap area and 70790 read back; 600 MB passed too (3 runs of 4: the fourth filled the swap area, and the app was stopped with "out of memory"). The swap area is used by the 512-byte sector, so a page that compresses to 300 bytes takes one sector, not 4 KB; the page pool leaves the kernel heap its last 1/32 and keeps 16 pages back for the swap bookkeeping, so memory can always be made. selftest 169/169 (64-bit) and 163/163 (32-bit), posixtest 71/71 and 59/59, Java (JitTest) at 384 MB.

- **Swap, part 1: compressed memory (build 182)** - when RAM runs low, the pages of apps' memory that were not used lately are **compressed in RAM** and their memory given back to the system; the moment an app touches one again, the page fault decompresses it (on whatever processor core the app runs) - what Windows 10 calls memory compression and Linux zram / zswap. It works on apps' mmap memory - a Java heap, big buffers - the memory that grows the most. An all-zero page takes no room, text and data typically shrink 3x (the kernel's own LZ compressor, `kernel/zswap.c`: ~1.3 KB for a 4 KB page), and a page that does not compress is kept aside as it is so the 2 MB pieces of RAM around it can still go back. Three pieces of groundwork came with it: apps' mmap pages now come from a **shared page pool** (`kernel/upage.c`) that returns each 2 MB piece to the system as soon as it is empty - before, an app kept every page it ever touched until it exited, even after unmapping it; a **TLB shootdown** (the other cores told, by an interrupt, to forget a page before its memory is used again - `munmap` and `mprotect` needed it too: another core could keep using an unmapped page); and the compressor task, which checks every 100 ms and keeps up with an app filling memory fast. `swap` shows what is compressed (`swap now` compresses everything idle, `swap off` stops it), `free` has a Swap line, Task Manager a "Compressed" line. Tested in QEMU: in a 192 MB machine with 141 MB free, an app mapped and filled **160 MB** - 20572 pages were compressed on the way, and all 40960 read back right; `selftest swap` (4 checks: 8192 pages compressed, 25 MB of RAM given back, every byte right after decompression, nothing left once unmapped). Java (its heap is mmap memory, now from the shared pool) passes JitTest and Bench at 2 GB and at 384 MB; `selftest` 169/169 (64-bit) and 163/163 (32-bit), `posixtest` 71/71 and 59/59. - **Faster updates and installs (build 177)** - `update` (and the installer's *Update (keep files)*) now rewrites only what changed. Install and update keep a **CRC-32C of every 64 KB** of the boot image in a small table at the end of the 128 MB boot area; an update reads the new CD, compares each piece's checksum with the table and writes only the pieces that differ - the disk is not read back at all, and when `update` has just compared, only the CD's changed megabytes are read again. A one-line change between two builds now writes 5 MB of the 71 MB image. The table names the image it describes (its ISO volume descriptor, which holds the time the CD was made), so a disk written any other way - by an older Banana OS, or half-way through an update cut off - is not trusted: it is compared and rewritten whole, as before, and gets a table for the next time. Measured in QEMU on an IDE disk and CD: an update with a small change **19 s -> 5 s** (compare 3.7 s + write 1.4 s), "already up to date" **12 s -> 3.7 s**; a delta update gives the very same bytes as a fresh install (checked byte for byte). Also: IDE disks and CD drives move data with `rep insw` / `rep outsw` (one string instruction per sector, where VirtualBox, VMware and KVM used to trap on every 16-bit word), and an IDE disk's write cache is flushed where the filesystem asks for it rather than after every command; reads are 1 MB at a time and AHCI commands up to 1 MB. Every boot of an installed system skips unpacking the built-in apps when they have not changed (~1 s saved: 16 MB of packages were unpacked each time just to be compared). `install` and `update` end with where the time went: "update: wrote 5 MB in 1.4 s (CD / stick 0.5 s, disk 0.5 s)". Tested in QEMU: install, update (delta, nothing to do, a disk without a table) on IDE and SATA, the built-in app upgrade after an update, `fstest` on an IDE FAT32 disk 15/15, `selftest` 159/159 (64-bit) and 157/157 (32-bit), `posixtest` 71/71 and 59/59.

- **`mmap` for apps** (build 162) - the first piece of a POSIX layer for ported programs, the way towards OpenJDK 17: `<sys/mman.h>` has `mmap`, `munmap` and `mprotect`. - **New in 0.6: the browser and Bing** - searching from Bing's home page works (one-line search boxes made of a `<textarea>`, as Bing and Google have, submit on Enter), `<base href>` and `data:` URLs (pictures, scripts, fetch), `Function.prototype.toString`, `in` inside a `for (...)` head's parentheses, and a layout fix for nested flex rows that made headers and some tables (Hacker News) far too wide or squeezed
- **New in 0.6: a real desktop, drag and drop, the Recycle Bin** - the desktop shows the files and folders of `~/Desktop` beside the programs (double-click opens them; right-click: Open, Show in Files, Cut, Copy, Delete, Rename; on the desktop itself: New folder, New text document, Paste, Arrange icons) and **icons stay where you drag them**. **Drag a box** to select several (desktop and Files; Ctrl+click adds one, Shift+click a range, Ctrl+A all). **Drag and drop**: files between Files' folders (onto a folder row or a place of the left pane), from Files onto the desktop and back, onto a desktop folder, onto a program's icon (it opens the file), onto the **Recycle Bin**; Ctrl held copies. **Delete** moves things to the Recycle Bin (`~/.Trash`; Shift+Delete, and on USB sticks: for good after asking); the Recycle Bin (desktop icon, Files' left pane) shows them with *Restore* (back where they were) and *Empty Recycle Bin*. Names starting with a dot are hidden in Files (Organize > Show hidden items)
- **New in 0.6: pin apps to the taskbar, icons-only or titles-only taskbar** - pinned programs sit right of Start (Browser and Files to begin with; a line under one shows it is open): right-click a window's taskbar button or an app's desktop icon - *Pin to taskbar*, right-click a pinned one - *Unpin*. **Settings > Taskbar** (or the taskbar's menu): *Icons and titles*, *Icons only*, *Titles only*
- **New in 0.6: the whole desktop by keyboard** - **Alt+Tab** (the window switcher; Shift goes back), **Win+Tab** (task view: every window as a card - arrows, Enter, Delete closes one), **Win+D** (the desktop: then the arrows go through its icons, Enter opens, the Menu key shows an icon's menu), **Win+T** (the taskbar's buttons), Win+E Files, Win+I Settings, Win+R a terminal, Win+L lock, Win+V the clipboard history (build 179), Win+M / Win+Down minimize, Win+Up bring back, Win+1...9 the taskbar's windows, Ctrl+Esc the Start menu, the **Menu key** or Shift+F10 (right-click menus, which the arrows and Enter drive). In **Settings, Task Manager and Apps**, Tab / Shift+Tab and the arrows move a yellow focus ring between the controls and Enter or Space presses them (Settings' file chooser: arrows, Enter, Tab through the places). Files, Notepad, the Browser and the Start menu had their keys already
- **New in 0.6: AMD, NVIDIA and Intel Arc / Xe graphics** - recognized by family (`lsgpu`, Settings > About: "NVIDIA GeForce RTX 30 series (Ampere)", "AMD Radeon RX 7000 series (RDNA 3)", "Intel Arc A-series (Alchemist)"...) and their screen made **write-combining**: the firmware leaves video memory uncached, so every pixel drawn was a trip over PCIe of its own - drawing is now many times faster on real PCs with these cards. The screen size is chosen in the boot menu or Settings > Screen (see below); there is no mode-setting or 3D driver for them
- **New in 0.6: Banana Code** - a code editor in the spirit of VS Code, with a **C compiler inside** (TinyCC): Explorer, tabs, syntax colours (C, JavaScript, HTML, CSS, Python, JSON, shell, Makefile, Markdown), find / replace, search in files, a command palette (Ctrl+Shift+P), Problems and Output. *New App* makes a desktop or console app; **F7 builds it on Banana OS itself** into a `.bpk`, **F5 builds, installs and runs it**. *Port a Program* turns a folder of C files (an existing program) into a Banana OS app, and the Problems list shows what does not compile yet. See [Banana Code](#banana-code)
- **New in 0.6: extensions, and a Claude extension** - Banana Code extensions are HTML + JavaScript views (the system browser's engine) that talk to the editor: read the file and the selection, insert code, open files, run builds, keep settings and make web requests with any headers. **Claude** comes built in: chat with Claude about your code with your own Anthropic API key - *Explain*, *Fix build errors* (it gets the compiler's messages), *Port to Banana OS* (it knows the SDK), *Review* - and put its code into the editor with one click
- **New in 0.6: the screen size on any PC** - without a graphics driver for the card (most real PCs: recent Intel, AMD, NVIDIA) Banana OS used to keep the firmware's size. Now Banana Boot asks the firmware (UEFI GOP or BIOS VBE) which sizes it offers: the boot menu shows a *Screen:* line (Left / Right to change it for this start), and *Settings > Screen* (or `resolution WxH` / `resolution auto`) saves the choice on an installed system - it is written into the disk's boot loader settings and used from the next start. With a graphics driver (QEMU, VirtualBox, VMware...) the size still changes at once
- **New in 0.6: fonts and text size** - *Settings > Fonts*: install your own TrueType fonts (*Install font...*, or right-click / double-click a `.ttf` in Files; they are kept in `/usr/share/fonts`), choose the **interface font** (the whole desktop's text) and the **documents font** (web pages, apps, desktop icon names), and the **text size** - Normal, Large, Larger, Largest - for terminal windows, Notepad and the desktop icons' names
- **New in 0.6: your own wallpapers in Settings** - *Settings > Wallpaper* now has *Your pictures*: the pictures you used lately (from *Browse...*, Files' *Set as desktop background* or Photos) as thumbnails next to the presets, and the position (Fill, Fit, Stretch, Center)
- **New in 0.6: Photos** - double-clicking a picture in Files opens it in the new Photos app (it used to become the wallpaper): the other pictures of the folder with Left / Right, zoom with the wheel or + / - (drag to move), 1:1 / fit, rotate, *Set as wallpaper*
- **Our own boot loader: Banana Boot** - GRUB is gone. One image boots on **legacy BIOS and UEFI**, from a **CD, a USB stick or a hard disk**, and starts the **64-bit or the 32-bit kernel** (the same menu as before, 64-bit by default when the CPU can). On BIOS: a 440-byte MBR or a 2 KiB El Torito entry loads a 10 KiB loader that runs in 32-bit protected mode and calls the BIOS through a real-mode thunk; it reads the kernel from the ISO9660 file system and sets the VBE graphics mode. On UEFI: `BOOTX64.EFI` (10 KiB, our C, no EDK2/gnu-efi) reads the kernel from its EFI partition, takes the GOP framebuffer and the firmware's memory map, leaves the firmware and steps down from 64-bit long mode to 32-bit protected mode. Both hand the kernels exactly what GRUB did (Multiboot2), so nothing changed for them - see [loader/](loader/)
- **A much bigger filesystem** - up to 65,536 files and 16,384 folders (was 1,024 and 256), found by name through hash tables, so a folder of thousands of files lists and opens as fast as a small one; files up to 128 MB. On an installed disk, files are read in the first time they are used instead of all at boot: what you can store is no longer limited by the RAM, and boot does not slow down as the disk fills. IDE disks larger than 128 GB are used whole (48-bit addressing)
- **File data is a cache** - like other systems, files in RAM are a cache of what is on the disk: when memory runs low, the files used longest ago are dropped from RAM (only once saved; a file in use is never dropped) and read in again when next used. Big files are read in pieces straight from the disk - apps and `play` never need a whole file in RAM (a song streams 64 KiB at a time) - and saving no longer copies a changed file first. `free` counts the droppable file data as "available"
- **`df`, `free` and `htop`** - `df` shows the disk space (size, used, free; `-i` files and folders, USB sticks too), `free` the RAM, `htop` a colour `top` with a meter per processor core, memory and disk. `top` now counts the RAM correctly (it showed only the files' data as used)
- **Apps and a Linux SDK** - write apps in C on Linux with the SDK in [`sdk/`](sdk/README.md) (C library with `float`/`double` and `math.h`, windows - resizable ones too - drawing, mouse/keyboard events, files, sound, HTTP); one `make` builds them for both kernels into a `.bpk` package. Install with `pkg install app.bpk` or a double-click in Files, run them by name or from **Apps** on the desktop. Six examples come built in (`~/Examples`)
- **Crash-safe apps** - an app that crashes (bad pointer, division by zero, stack overflow...) is stopped with a message saying what happened, and the rest of the system keeps running; on the 64-bit kernel NULL pointers and stack overflows (guard pages) always fault. Every task's FPU/SSE registers are saved, so apps compute in floating point
- **USB sticks (FAT32)** - plugged-in sticks are mounted at `/mnt/usb`, read and write, long file names included; every tool works on them (`ls`, `cp`, Files, the browser, `pkg install`...). `umount` ejects
- **NVMe SSDs** - a polled NVMe driver: NVMe disks are install targets (and boot on UEFI), FAT32 partitions are mounted at `/mnt/nvme`
- **virtio disks** - virtio-blk (QEMU/KVM, Proxmox, cloud VMs): install targets like NVMe, FAT32 partitions mounted at `/mnt/virtio`; virtio disks and network cards work over the legacy and the modern (virtio 1.x only) interface
- **SD card readers and eMMC** - SDHCI controllers (PCI): SD, SDHC and SDXC cards are mounted at `/mnt/sd` when put in and unmounted when taken out; eMMC chips (and MMC cards) at `/mnt/mmc`. Both are install targets
- **SCSI disks** - virtio-scsi (QEMU/KVM, Proxmox's *VirtIO SCSI* and *VirtIO SCSI single*): every target and LUN, install targets like virtio, FAT32 partitions mounted at `/mnt/scsi`
- **Firewall (optional)** - off unless turned on (`firewall on`, Settings > Network): connections from outside refused but for the ports allowed (`firewall allow tcp 22`), pings only if allowed, everything you start works as before; `firewall log` shows what was blocked
- **IPv6 (optional)** - off by default; `toggle6 [on|off]`, `ipv6 on/off` and Settings > Network control the same switch. Link-local/SLAAC addresses, neighbour discovery, ping, TCP, UDP and AAAA DNS. IPv4 stays independent. `curl -6` and `wget -6` select IPv6; bracket literal addresses, e.g. `http://[::1]:8080/`. Use `selftest ipv6` for local checks; it restores the previous toggle state without changing saved settings.
- **Intel Macs** - Apple keyboards (Command works as Ctrl), Apple NVMe SSDs (2015-2017 Macs, T2 Macs), the speakers of Macs' HD Audio codecs (GPIO amplifiers), and the Apple SMC's temperatures and fans in `sensors`
- **Android phones** - `adb` (devices, shell, push, pull, install, logcat, reboot) and `fastboot` (getvar, flash, erase, boot, reboot, oem, flashing unlock) over USB, with the phone's "Allow USB debugging?" key check (RSA-2048, the key in `~/.android`)
- **Drag and drop everywhere** - files dragged from Files or the desktop onto a terminal type their paths at the prompt, onto Notepad / the Browser open there, onto an app's window go to the app (Banana Code, Photos, Media Player, Music; API 13 `BANANA_EV_DROP`); held over a taskbar button, that window comes up to drop on
- **Game controllers** - USB gamepads and joysticks (HID: PlayStation, Logitech...), Xbox 360 and Xbox One / Series controllers, in one layout for apps (API 12, `banana_gamepad`); `gamepad` shows them
- **CPU temperature** - `sensors` and Task Manager show the processor's temperature (Intel digital thermal sensor, AMD Tctl; not in virtual machines)
- **Power button** - the ACPI power button (and VirtualBox's ACPI Shutdown, QEMU's `system_powerdown`) saves the files and shuts down
- **Sound** - Intel HD Audio (any codec: Realtek ALC, IDT/SigmaTel, Conexant, VIA... - every analog output, speakers and headphones together), AC'97 and USB audio (headsets, USB speakers, DACs) drivers (QEMU, VirtualBox, real PCs) and the PC speaker: `play file.wav`, `beep`, `volume`, and sound for apps
- **Windows-like taskbar** - a button per open window (click: focus, click again: minimize), minimize buttons, *Show the desktop*
- **Task Manager** - windows and apps (Switch to / End task), the kernel's tasks with their CPU use, live CPU and memory graphs; from the desktop, the Start menu or a right-click on the taskbar
- **Settings** - wallpaper, fonts and text size, screen resolution, sound volume, keyboard layout, mouse pointer speed, network, date & time and information about the computer (`settings` in a terminal); volume, layout and pointer speed are kept in `/etc/settings.conf`
- **Window buttons** - every window has minimize, maximize / restore and close buttons in its title bar
- **Right-click menus everywhere** - desktop, taskbar, terminals (copy, paste, clear), Files (open, install, rename, cut/copy/paste, delete, new file/folder, eject), the browser (open/save link, back, reload, page source...), Notepad
- **Browser downloads** - anything that is not a web page (apps, archives, programs...) is saved to `~/Downloads`; *Save link as* / *Save page as* in the right-click menu

## 0.5

- **64-bit** - the kernel also builds for x86_64 (long mode, 4 GiB identity-mapped with 2 MiB pages); one ISO carries both kernels and its boot menu picks the 64-bit one when the CPU supports it, the 32-bit one otherwise
- **UEFI** - the ISO (and a disk made with `install`) boots on UEFI firmware as well as on BIOS; `neofetch` shows which one started it
- **Networking** - PCI NIC drivers (Intel e1000 - 82540EM / 82543GC / 82545EM, QEMU's default and VirtualBox's PRO/1000 cards; AMD PCnet-PCI II and PCnet-FAST III, VirtualBox's AMD cards; virtio-net, VirtualBox's paravirtualized card; Realtek RTL8139; Realtek RTL8111/8168, RTL8169 and RTL8101/8102, the gigabit Ethernet of most PC mainboards) and a from-scratch TCP/IP stack: Ethernet, ARP, IPv4, ICMP, UDP, DHCP, DNS and TCP (retransmission with RTT-based timeouts, fast retransmit, congestion + flow control, out-of-order reassembly)
- **`ping`, `curl`, `wget`, `nslookup`, `ifconfig`, `netstat`, `arp`, `dhcp`** - working against real hosts; a download whose connection breaks or stalls goes on where it stopped (HTTP `Range`), for curl, the browser and apps alike
- **USB** - xHCI, EHCI and UHCI host controllers and USB hubs (on EHCI/UHCI, including the hub Intel chipsets put behind every port), USB keyboards, mice and sticks, and USB network adapters: **Realtek RTL8152/8152B (Lanberg NC-0100-01)** and CDC-ECM; `lsusb`, hot-plug with `usb rescan`
- **HTTPS** - a TLS 1.3 client (X25519, AES-128-GCM, ChaCha20-Poly1305, SHA-256/HKDF, all written from the RFCs, with known-answer self-tests: `cryptotest`)
- **Your own wallpapers** - download a PNG/JPEG/BMP/GIF with `wget` (or `wallpaper url ...`) and use it; pick it in the Wallpaper app or with the `wallpaper` command. The choice is saved and survives reboots on an installed disk
- **Real files** - files are no longer capped at 2 KiB: data lives on a new kernel heap (up to 32 MiB per file), binary files are fine, and installed disks from 0.4 are upgraded automatically
- **Faster, cooler** - timer interrupts + `hlt` instead of busy polling: an idle Banana OS went from pinning a host CPU core at **100% to ~6%**; the console prints ~100x faster (an 8000-line file: 27.8 s -> 0.27 s); the desktop only repaints what changed
- **Serial console** - the shell also runs on COM1 (`-serial stdio`), which makes Banana OS scriptable and testable headless
- **SSH server** - log in from any SSH client (OpenSSH, PuTTY, Windows `ssh`) with the password you set with `passwd`: curve25519 key exchange, Ed25519 host key, ChaCha20-Poly1305 / AES-128-GCM, written from the RFCs
- **Web server** - `httpd start` serves `/var/www` (with folder listings) to any browser on the network
- **File explorer** - a "Files" window on the desktop: browse, preview text and pictures, new folder, delete, open in the editor or a terminal, set a picture as the wallpaper
- **Web browser** - a "Browser" window on the desktop with its own HTML parser, CSS engine, layout and renderer, and a small JavaScript interpreter with a DOM (`getElementById`, `innerHTML`, events, `setInterval`, ...); opens `http://`, `https://`, `file://` and `about:home`
- **Browser framework checks (build 166)** - offline React 18.3.1, Vue 3.5.13 and Alpine 3.14.9 counters with compiled Tailwind CSS 3.4.17, plus a real Astro 5.13.2 production build with Preact islands (`client:load`, `client:idle`, `client:only`). Run `selftest browser swm` for the live SuperWebManager baseline (16 host checks pass, including WebP images and desktop grid). Latest layout/image fixes await VM confirmation. These demos cover a subset; Tailwind v4 and the CDN compiler are not verified. See [fixture sources and host tests](web/fixtures/README.md).
- **PHP** - `httpd` runs `.php` pages (`$_GET`, `$_SERVER`, `header()`, ~90 functions, files) with the same interpreter; try `http://localhost/demo.php`
- **Permanent settings** - the network configuration (static IP or DHCP, chosen interface) and the servers to start at boot are saved in `/etc` and applied at every boot of an installed system
- **Shell** - output redirection (`cmd > file`, `cmd >> file`) and command lists (`a; b`, `a && b`)
- **SATA** - an AHCI driver next to the IDE one: SATA hard disks and SATA CD/DVD drives (QEMU `-machine q35`, VirtualBox's SATA controller); `install`, `sync` and booting from the disk work on either; `disks` lists them
- **Resizable windows** - terminals, Files, Browser and Notepad resize from their bottom-right corner, and a double-click on a title bar maximizes / restores; a terminal's shell and the editor follow its new size
- **Copy and paste** - one clipboard for the whole desktop: drag over a terminal's text to copy it and right-click to paste; Ctrl+C / Ctrl+X / Ctrl+V in Notepad, the editor and the browser
- **Notepad** - a GUI text editor window (`notepad [file]`, the desktop, or double-click a text file in Files): mouse selection, scrollbars, Open / Save / Save as / Find
